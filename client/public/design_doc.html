System Architecture & Design Document: Listen Together

Music Streaming with Shared Listening Rooms & Sub-200ms Synchronized Playback

Scale & Target Requirements:
  • 20 Million MAU | 2 Million peak concurrent listeners
  • 50 Million track catalogue
  • 200,000 shared rooms open at peak (2 up to 5,000 listeners per room)
  • Playback sync accuracy: sub-200ms across all participants worldwide

1. Executive Summary

This document details the complete backend architecture for a high-scale music streaming service featuring real-time collaborative listening rooms ("Listen Together"), comparable to Spotify Group Sessions and Discord Watch Together. The architecture decouples static audio asset delivery (handled by an Anycast Global CDN with HLS adaptive bitrate chunks) from real-time room state orchestration (powered by WebSocket gateways and a Redis Pub/Sub cluster).

3. Core System Components

3.1 Audio Delivery: Storage, Encoding, CDN & Fast Playback Start

  • Encoding Pipeline: Origin masters (FLAC) are sliced into 3-second segments and encoded in AAC-LC (96k, 160k, 320k) and Opus (24k, 64k, 128k) using HLS and MPEG-DASH.
  • Fast Playback Start: The manifest serves a lightweight initialization chunk (0.5s segment), initiating audio playback in < 150ms before stepping up bitrate via Adaptive Bitrate (ABR).
  • CDN Caching: Chunks are content-addressed (`trk_982_160k_seg042.m4s`) with 1-year immutable caching. Edge hit ratios exceed 99.2%.

3.2 Catalogue & Search

  • Metadata Storage: PostgreSQL Aurora guarantees relational integrity across 50M tracks, artists, and rights.
  • Search-as-you-type: Elasticsearch index using edge N-grams and completion suggesters executes typo-tolerant prefix search in < 30ms.
  • Publishing New Releases: Tracks are pre-indexed with UTC embargo dates. A Redis trigger activates new releases instantly without database table scans.

3.3 Room Sync & Sub-200ms Drift Correction

  • NTP Clock Offset Calculation: Clients calculate round-trip latency on connect: Offset = ((T1 - T0) + (T2 - T3)) / 2.
  • Smooth Micro-Adjustment Algorithm:
    • drift < 50ms: No adjustment (imperceptible).
    • 50ms ≤ drift ≤ 500ms: Audio player speed is micro-adjusted to 0.95x or 1.05x for 2 seconds. Zero audible audio clicks or pauses!
    • drift > 500ms: Hard seek to server time.
  • Shared Queue: Conflict-Free Replicated Data Types (CRDT - LSEQ) handle concurrent playlist additions and "Vote to Skip" voting across 5,000 users without row locks.

4. Reliability, Failure Scenarios & Observability

4.1 Zero-Downtime Deployments for Live Rooms

Using Envoy connection draining, terminating pods stop taking new connections and send a WebSocket frame instructing clients to reconnect over a staggered jitter window (100–3000ms). Active listening rooms experience uninterrupted playback.

4.2 Five Critical Failure Scenarios Handled

  1. Regional Outage (e.g. AWS us-east-1 goes down): Multi-region Active-Active architecture fails over DNS to us-west-2 within 15 seconds. DynamoDB Global Tables retain room state. Clients reconnect automatically.
  2. Sync Node Dies with 1,000 Live Listeners: Dropped sockets reconnect with exponential backoff. Healthy nodes reload state from DynamoDB and re-sync listeners within 400ms.
  3. Redis Pub/Sub Partition: Sentinel failover promotes replica in 3 seconds. If Pub/Sub is unavailable, nodes gracefully degrade to DynamoDB polling every 2 seconds.
  4. Royalties / Analytics DB Spike: Kafka queues buffer up to 7 days of raw play events on disk, ensuring zero revenue loss during database maintenance.
  5. Jittery Client Network: Adaptive Bitrate drops audio to 64kbps Opus while keeping WebSocket connection active, micro-accelerating (1.05x) to catch up once buffer refills.

4.3 Observability: Proving Sync Actually Works

  • client_sync_drift_ms (p50, p95, p99): Telemetry reported by clients every 30s. Alerts if p95 > 180ms.
  • sync_heartbeat_rtt_ms: WebSocket ping-pong latency.
  • buffer_underrun_rate: Percentage of clients experiencing audio stutter.
  • fanout_broadcast_latency_ms: Latency from host pause to final client delivery.

5. Team of Three: Roadmap & MVP Strategy

Phase 1: What to Build First (Months 1–3)

  1. Static Audio via S3 + CloudFront CDN (single 160kbps AAC bitrate).
  2. Minimal Sync Engine with Node.js + Socket.io + Redis Pub/Sub for host play/pause.
  3. Relational catalog in PostgreSQL with basic ILIKE search.
  4. Host-driven queue in Redis.

Phase 2: Postponed to Scale (V2 & Beyond)

  1. Elasticsearch search-as-you-type (defer until catalog surpasses 1M tracks).
  2. Multi-bitrate Adaptive HLS encoding.
  3. Kafka + ClickHouse big-data royalty pipeline (use async Postgres tables initially).
  4. Active-Active Multi-Region infrastructure.
  5. CRDT democratic voting queue.
